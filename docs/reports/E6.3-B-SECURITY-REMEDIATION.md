## 1. The defect being remediated (pre-E6.3 state)

Production LiteLLM (`litellm-personal`, host port 4101) carried **plaintext `x-consumer-key` values in the `extra_headers` of 6 model rows** (`rag-mizan`, `rag-general`, `rag-fiqh`, `portal-rag-mizan`, `portal-rag-general`, `portal-rag-fiqh`). Anyone who could read the model config (DB, `/model/info`, or an admin session) obtained the consumer keys of the other product (radio vs. portal) — a cross-product privilege path. In addition, the **LiteLLM master key had appeared in plaintext in an untracked local script** on the operator workstation (B3-L1) and therefore had to be treated as leaked.

Remediation goal: **no consumer key ever appears in LiteLLM config again**; each consumer's key is injected server-side by a dedicated forwarder that is itself keyless from the network's point of view (no published ports).

## 3. B2 — Consumer-key forwarder (staging prototype → production chain)

### 3.1 Architecture

```
UI (radio_api / ragportal_api)
  └─ RAG_LITELLM_URL → LiteLLM :4101  (api_base = Fernet-encrypted in DB; no xck in extra_headers — count = 0)
        └─ model rows point at the forwarder:
             radio  models (rag-mizan/rag-general/rag-fiqh)        → rag-keyfwd :8211
             portal models (portal-rag-mizan/-general/-fiqh)       → rag-keyfwd :8212
rag-keyfwd (container, python:3.12-alpine, NO published ports)
  │  directory mount /home/saber/e63-b2-keyfwd → /opt/keyfwd:ro
  │  code: rag_keyfwd.py  (12,435 B, LF)  sha256 56e7fb336a949894973c755e17d7fc351d48d61b602c628b25aa87f1c527d04a
  │  (tracked copy: _e63_b2_keyfwd/rag_keyfwd.py + test_keyfwd.py — the only VCS copy until dedicated-rag is pushed, see C1)
  └─ for every forwarded request: OVERWRITES `x-consumer-key` with the
     per-consumer key from keys.json (flat format), fail-closed (None → 401),
     mtime+size hot-reload, healthz exposes key DIGESTS only
        └─ upstream http://10.240.17.1:8210 (RAG gateway, host-network)
             gateway inbound auth (api.py L90-119): Bearer GATEWAY_SERVICE_KEY +
             x-consumer-key → registry verify_consumer → 401 unknown_consumer_key if bad
```

Security properties: (1) the client's `x-consumer-key` is always overwritten — a spoofed header cannot escalate to another consumer; (2) key material exists only in the forwarder's keyfile (600) and the registry (hashed) — never in LiteLLM, never on a published port; (3) key digests (sha256-16) in `healthz`/evidence, raw values only in the keyfile.

The hang was already reproducible **before** B2 (browser test T17, 2026-11-16T16:53:35Z). Full diagnosis: [`evidence/E6.3/security/e63-b2-p6-1b-public-rag-blocked.md`](../../evidence/E6.3/security/e63-b2-p6-1b-public-rag-blocked.md) and `evidence/E6.3/network/e63-a2-connectivity.md`.

**Owner fix:** ALLOW TCP `172.20.1.53 → 172.30.0.133:4101` (required — RAG chat), `:8200` (source picker), `:8210` (recommended — direct gateway). Do NOT open :4000/:4102 (other products).
