- **F-H6-6 (MEDIUM):** Backup cadence is event-driven, not time-driven. A week without deploys = a week without dumps. Recommend a scheduled `pg_dump` of litellm + `cp` of rag-registry.db + docker image `save` for RAG images, with the K1/K2 naming convention from H4.

## 3. Disaster-recovery readiness

| DR dimension | State |
|---|---|
| RAG core (gateway/registry/litellm/keyfwd/mizan/fiqh) | single host s52; compose-defined but no second instance anywhere |
| LLM (vLLM 27B, H200 GPU) | single host s53; **no failover GPU box**; model weights local to `/models/` on s53 |
| UI (rag-portal, radio-rag-service) | single host s53 (staging twins on s53 as well, different lanes) |
| Data | litellm DB: local dumps only (H4); rag-registry.db: local file only; keyfwd state: in-container/local only |
| Restore runbook | E8.0-G deploy script does backup-then-deploy; **no standalone restore procedure was found** and no restore has been tested off the original host |
| Log retention | s52 loki local; s53 logs → unregistered 172.20.1.22 (F-H6-3) |
| Alerting | none (F-H6-2) |

**F-H6-7 (DR_READINESS = NOT_READY):** For every RAG-critical asset there is exactly one live instance and at most one same-host backup copy. Recovery from s52 disk loss is *possible* (compose + local images + yesterday's dumps) but **untested as DR**; recovery from s53 loss means losing the only 27B inference endpoint with no warm spare. No component has a cross-host failover path, and the absence of alerting (F-H6-2) means a silent outage would go undetected.

**F-H6-8 (carried from H5, S-X53-1):** s53 has no effective host firewall (5432/6379/7687/8000 etc. OPEN from the operator-network vantage). This is both a security and a DR/abuse risk (unauth vLLM = free GPU; unauth postgres/redis = data exfiltration vector), and it raises the blast radius of s53 compromise. Detail in `E8.0-H5-LLM-ENDPOINT-TUNNEL-AUDIT.md` §3.

## 4. What would move the verdicts (recommendations, no action taken)

1. **OBSERVABILITY → READY** would require: (a) a `/metrics` endpoint on rag-gateway (fixes C3-1) or a black-box probe set; (b) scrape jobs for rag-gateway/rag-registry/litellm-personal/rag-keyfwd; (c) remove the zombie `ft-serving-05b-53` target; (d) an alertmanager (or at minimum uptime checks with notification); (e) register 172.20.1.22 in the inventory or move s53's promtail to s52's Loki.
2. **OFFSITE_BACKUP → VERIFIED_PRESENT** would require: any one of (a) a scheduled `rclone`/`restic`/`rsync` job to a second host/object store, (b) a network mount with scheduled copy — plus a **tested restore** to prove integrity.
3. **DR_READINESS → READY** requires the above plus a documented, **executed** restore drill for at least litellm DB + rag-registry.db + one RAG image, and a plan for GPU failover (even a documented "re-provision vllm-qwen38 from /models + saved image, ETA Xh" runbook would move it to CONDITIONAL).
