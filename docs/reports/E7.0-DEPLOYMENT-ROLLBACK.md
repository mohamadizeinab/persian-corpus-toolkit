## 2. Rollback per change (ordered — most recent first)

### 2.1 B2 production (forwarder + 6 model rows + consumer-key rotation)

**Precondition:** none (K2 + K3 are self-sufficient). If B1 is also to be rolled back, do 2.1 **first**, then 2.2 (row-level state is MKEY-era-independent only while the forwarder is down — keeping the ordering simple: B2 before B1).

```bash

cd /home/saber/backups/e63-b2-20261117-000829 && sha256sum -c SHA256SUMS   # 1. verify snapshot

# 2. restore pre-patch model rows (6 rows: api_base back to gateway :8210,
#    x-consumer-key back in extra_headers) via the LiteLLM admin API:
#    for each row in model-info-pre.json: POST /model/update (or DELETE + /model/new)
# 3. restore OLD consumer keys:
cp keys.json.pre-rotate.keys.json.new keys.json    # i.e. copy K3 over live keys.json (600)
# 4. stop + remove the forwarder container:

# 6. verify the pre-B2 state:
curl -s http://127.0.0.1:8200/health          # {"enabled":2,...,"ok":true}

#    NEW (rotated) key → 401 unknown_consumer_key
```

State that does **not** roll back (and does not need to): registry audit rows (append-only, additive), the disabled temp consumers `e6-b4-prod` / `e6-c6-temp` / `e6-c6-temp2` (disabled = inert; no delete endpoint exists), the archived `e6-acceptance` provider (C6 v2) and its prompt version 1 (archived = invisible to routing), registry `version` token (self-healing cache-invalidation value).

### 2.5 Hotfixed images (prod registry/gateway docker-cp)

The prod `rag-registry` / `rag-gateway` host-network containers carry a docker-cp hotfix (K5). Rollback = docker-cp the **original** files back from a pristine image layer:

```bash
docker run --rm -v /tmp/orig:/out $(docker images -q rag-gateway:0.1.0 | head -1) \
  sh -c 'cp -r /app /out'     # then docker cp the original files back into the container,
docker restart rag-gateway rag-registry
```
(Prefer simply re-running K5 forward — the hotfix is the accepted current state; rollback is only needed if the hotfix itself misbehaves.)

## 3. Post-rollback verification checklist (apply after ANY rollback)

1. `PRAGMA integrity_check` = `ok` on the touched SQLite DB; row counts match K1/K2 (`sqlite3 … "SELECT COUNT(*) …"`).
2. Registry: `:8200/health` ok, `providers_enabled=2`, version token present.
3. Gateway: `:8210/v1/chat/completions` with the **current-era** consumer key → 200; the other era's key → 401.
4. LiteLLM: `:4101/health/liveliness` 200; `/model/info` row set matches the era you rolled to (6 rows, correct `api_base`).
5. Public smoke: `python _e63_b2_public_smoke.py` (s52-local chain) green ×3.
6. Browser (if UI-adjacent): T02/T12 matrix unchanged (graceful 502 under P6-1 still expected until the firewall opens — that is the network, not the rollback).
7. Log the rollback into the next G-register report entry; keep the forward backups (do not delete K1–K5 until the rolled-forward state is stable for one full day).
