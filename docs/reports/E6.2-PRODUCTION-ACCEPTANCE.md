## 3. Gap G1 / P6-1 — THE blocker (public UI path)

**Status: BLOCKED (external owner action required).**

### 3.1 Symptom

From s53, connections to s52 ports **4101, 8200, 8210** (and even :22) time out. Consequences:

- Public radio `radio.ai.ismc.ir` and portal `rag.ai.ismc.ir` → their `/api/rag/sources` (and any RAG chat via the new path) fail with **502 `registry_unreachable` / upstream unreachable**.
- Direct server-to-server from s52 localhost works (that is how all §9–§13 evidence was generated).
- Legacy radio (via s52:4000) still works — :4000 is the **only** port of the s52 RAG set reachable from s53.

### 3.2 Root cause (verified)

s52 host firewall: `iptables` default-drops s53 → s52 on those ports; only :4000 has an ACCEPT. This was **already identified in E6.1 as P6-1** (see `..\rag\rag-portal-patches\E6.1-PHASE9-FINAL-REPORT.md` §blockers) and was left to the owner because it requires `sudo` on s52.

### 3.3 Owner fix (exact command, one line + persist)

```bash
# on s52, as root
sudo iptables -I DOCKER-USER -s 172.20.1.53 -p tcp -m multiport --dports 4101,8200,8210 -j ACCEPT
sudo netfilter-persistent save
```

### 3.4 Verification after fix (owner can run, no SSH needed from owner)

1. `radio.ai.ismc.ir` → open chat, ask **«مضمون سوره حمد چیست؟»** → expect a grounded answer with المیزان citations within ~30–90 s.
2. `rag.ai.ismc.ir` → same question → same expectation.
3. `/api/rag/sources` on both sites must return the registry list (mizan + fiqh) instead of 502.
4. Gateway audit (`GET /v1/audit`, service key) should show new `ok` entries with `consumer_id` `radio`/`portal`.

### 3.5 Why this blocks (and only this blocks)

The mission chain **starts at the human UI**. With the firewall rule absent, a human in a browser cannot complete the chain — everything downstream is proven working (§9–§13), so this is a single, identified, externally-owned prerequisite, not a platform defect.
